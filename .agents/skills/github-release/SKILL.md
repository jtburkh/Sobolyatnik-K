# Sobolyatnik-K GitHub releases

This skill belongs to the public `Sobolyatnik-K` repository. The private Beads workspace is `/home/jtburkh/RtV-Toolkit`; run `bd prime` there, record open validation/release issues, and **never** add its files, private saves, extracted game scripts/resources, or `/tmp` materials to the public Git repo. Source pushes, GitHub release publication, gameplay installation, and Nexusmods uploads are *different authorizations*. Do not commit or push without the owner's explicit approval for this release. Do not edit published tags or asset bytes to fix a defect: create a separately versioned release.

## Identify the release

1. `git status -sb`, `git remote -v`, and `git ls-remote origin refs/heads/main refs/tags/<new-tag>`; stop for unexpected worktree edits, remote drift, or an existing tag. Keep prior immutable tags untouched. Compare the actual public release API tag and filenames, not just Git tags: a tag can exist with a different GitHub Releases alias. Preserve the owner's GitHub-web README edits when updating docs.
2. Bump `Cargo.toml`, `Cargo.lock`, and `godot-mod/rtv-radar-range/mod.txt` to the **same SemVer** before a code push. The Toolkit `--help`, generated VMZ `mod.txt`, wrapper, receipt, Windows app label, GitHub tag, workflow title, release ZIP, and README must agree. A short player-facing name such as **Sobolyatnik-K v1.1** may correspond to internal/tag version `1.1.0` / `v1.1.0`. Check any old hardcoded version in `.github/workflows/ci.yml`, the versioned release workflow, and `tools/build_hotfix_test_kit.py`; never modify historical installer templates or already published bundles.
3. If the game changed, review its contracts **read-only** and resync only derived `data/*.json` from recovered files **outside Git** following `docs/catalog-sync.md`. Verify original catalog paths remain and inventory sizes are not guessed. Match official Metro release hashes and license; never replace an installed loader without a separately authorized migration. Keep F7/F8/F9, visible Shot Alerts, five-second scene-local markers, display-only ranges, and no `AI.PlayFire` hook.

## Gate source changes

- Run `python3 tools/check_steam_build.py` **before every push** (including docs-only): advisory on source pushes, report public/local/installer IDs, and never relax an old installer merely to silence it. For a release use `--strict --installer <generated-bundle>/install-sobolyatnik.ps1`; compare to the live Steam public build and depot. Strict identity is NOT gameplay clearance.
- Run `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features --locked -- -D warnings`, `cargo test --locked`, and Python suites under `tests/version`, `tests/catalog`, and `tests/steam`. Run `git diff --check` and verify `git status` contains only intentional public files.
- Build the Windows x64 Toolkit from the same source/lockfile, execute its `--help`, assemble with `tools/build_hotfix_test_kit.py` using hash-verified official Metro files, and package with `tools/zip_hotfix_test_kit.py`. Verify the ZIP and all member hashes, and run `tools/test_radar_shots.py --player-bundle` using the pinned Godot engine. Run `tests/installer/hotfix-preview-smoke.ps1`, `bundle-smoke.ps1`, and the migration smoke on **synthetic game paths only**. Never run fixture `-TestIntegration` on a machine with a real installed Sobolyatnik-K Windows registration; that test deletes its test registry key. A real running RTV process must still block the production installer. Owner-reported gameplay on an earlier VMZ is not a test of a new one.

## Publish in two phases; do not break the live README

**Phase A — source:** Keep the README's one recommended command pointing at the *currently public, verified* release until new public assets exist. Commit the reviewed version bump, build scripts, versioned workflow, tests, and any safe docs fix; push `main` only with explicit approval. Inspect the actual GitHub Actions `CI` run and stop on any failure. Fetch/compare the remote before committing or pushing; do not rebase away the owner's web edits. Source-only CI artifacts are not GitHub release assets.

**Phase B — versioned release:** Require a fresh tag matching the workflow's exact trigger. Use `git tag <new-tag>` on the CI-tested source commit and push **only that new tag**, with the owner's release authority. The versioned Actions workflow must fail closed on a pre-existing release/API errors, build MSVC EXE, obtain Metro by HTTPS with pinned SHA-256, test Windows installation/rollback and exact player VMZ, and check current Steam identity strictly before `softprops/action-gh-release` publishes. Watch the workflow/API until complete. Download **public** ZIP and checksum from its release tag, verify the ZIP SHA-256, member list and each internal VMZ/EXE checksum, and confirm version/title/tag/asset names and release visibility. Never claim release published when only a tag or CI artifact exists. If anything fails, stop and report the precise failure; fix via a *new version*, not asset replacement.

**Phase C — player README:** Only after the public release assets verify, update the README to **one** PowerShell copy/paste line that fetches the actual release ZIP and adjacent `.sha256`, checks the checksum *before extraction/installation*, and invokes the included offline `run-sobolyatnik.ps1`. Explain that a different existing bundle must be uninstalled through Windows Installed apps first (Metro, saves and backups retained); do not silently overwrite. Keep cache reconciliation inside the new installer, not a separate alarming README repair block. State the reviewed game build and warn that other valid builds can install but are unverified; do not describe synthetic tests as broad crash-free clearance. Update the matching installation guide and release-metadata tests **as part of the versioned source commit** to accept staged (old or new) README guidance, so the later docs-only promotion doesn't need another code version bump. Re-run docs/tests, pre-push Steam advisory, commit and push the docs-only change with approval, and verify the *rendered public* README and download command. Preserve older docs/tags without promoting failed versions.

A Git SSH key only authorizes Git operations, **not** authenticated GitHub Releases API edits. If release API authentication or Actions permissions are blocked, report it; never claim a draft was made public or a public release hidden without authenticated verification.

## Nexusmods is a separate channel

Tracked in private Beads as `RtV-Toolkit-lew`: future ZIP `Sobolyatnik-Kv.x.x.x-Nexusmods.zip` must contain only the exact tagged VMZ and a snapshot of GitHub player README; **NO EXE** or executable-containing full GitHub bundle. Do not build/upload to Nexus or silently replace GitHub's Windows package with that VMZ-only ZIP until its skill, allow-list packaging tests, and owner upload authorization exist.
