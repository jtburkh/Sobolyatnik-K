# Summon controls — v1.2.0 development and validation record

The versioned source adds paired in-game and Windows Toolkit controls for **one CASA airdrop, the Punisher, or the Bogeyman** on reviewed Steam build **25837777**. The previously published v1.1 has **no summon receiver**. An owner-authorized local v1.2 trial was installed after backing up v0.1.16 and normal save/config data; the owner observed the CASA drop and both boss encounters and kills. A game-closed read-only audit corroborated these encounters in the latest session log, which contained no script errors and ended in normal saves. This is **one session**, not proof of broad crash-free compatibility. Toolkit-triggered summon actions have not been validated in real gameplay. Only install another build when the game is closed, with owner permission and verified rollback.

## Controls

- **In game:** With a playable scene and visible radar, press **F10** to open/cycle `CASA AIRDROP → PUNISHER → BOGEYMAN`; **F11** confirms within eight seconds. F8 hides the HUD and cancels selection. The HUD stays mouse-pass-through, never hijacks F7/F8/F9, and does not hook or rewrite AI fire. A 15-second cooldown prevents rapid repeated requests; the HUD reports *queued* or why the action was rejected, not proof of subsequent gameplay completion.
- **Toolkit Radar tab:** With fresh live snapshots from a compatible summon-capable VMZ, press **p** for airdrop, **b** for Punisher, or **Shift+B** for Bogeyman, then **y/Enter** to confirm. The Toolkit rechecks capability before queuing and shows the game's accepted/rejected result for the matching request ID or a timeout. Published v1.1 radar packets do **not** advertise summon capability, so these controls remain disabled with that mod. Historical standalone `--spawn-airdrop` / `--spawn-boss` CLI flags are deliberately disabled, rather than writing requests that a v1.1 VMZ cannot consume.

Both surfaces use the game's existing `EventSystem.Airdrop()` or `AISpawner.SpawnBoss()` paths, not arbitrary scenes/positions. Punisher needs its remaining native pooled instance and current-map distant `AI_SP` plus `AI_WP`, with `Attack` state. Bogeyman needs its remaining pooled instance and distant current-map `AI_LP`, with `Lurk` state. Invalid/missing instances or spawn points fail closed. Native boss pools contain one of each per initialized scene. The candidate accepts only fixed actions, rejects malformed/expired (>30-second) or duplicate Toolkit requests, removes the request **before** deferring the native call, and writes a result file alongside—not inside—the character save. A queued call is not a guarantee that a cinematic or AI encounter completed.

## Isolated verification

`python3 tools/test_radar_summons.py --engine /path/to/Godot_v4.6.3-stable_linux.x86_64` builds `dist/probes/RtVRadarSummonsCandidate.vmz` with manifest `1.2.0` and runs synthetic game-method, UI, stale/duplicate-request and boss-pool tests. `python3 tools/test_radar_shots.py --engine /path/to/Godot_v4.6.3-stable_linux.x86_64 --player-bundle dist/probes/RtVRadarSummonsCandidate.vmz` verifies F7/F8/F9 and shot fade unchanged. `cargo test --locked --all-targets`, `cargo clippy --locked --all-targets -- -D warnings`, and the version/build gates cover the Toolkit and packaging. The local Windows bundle passed native EXE launch, checksum/extraction, fake-game install/uninstall/cache/conflict fixtures and hash-pinned migrations from the public v0.1.16 and v1.1 ZIPs. The versioned release workflow additionally builds and tests a new Windows MSVC Toolkit, checks the exact downloadable VMZ in Godot mocks and requires strict current Steam identity before publishing. Review workflow results and public bytes before updating the README's single recommended install command. Neither fixtures nor game-build identity establishes broad gameplay safety.
